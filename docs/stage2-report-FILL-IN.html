1. Project overview and implementation status

1.1 What the application is

The AI Code Review Agent is a desktop tool that reviews source code. A developer points it at a repository; the agent indexes it, and can then explain code, detect defects and grade them by severity, check a project coding standard, propose refactorings, write unit tests, answer questions about the codebase in natural language, compare review results across two versions, and export a report.

Beyond those request-response features, the agent can be given a goal in plain language and left to pursue it on its own: it writes a plan, chooses which of its tools to invoke, reads the code it decides is relevant, records findings, and writes a synthesis when it judges the goal met.

1.2 Users

  • Software developers reviewing their own work before opening a pull request.
  • QA engineers looking for defects and missing test coverage.
  • Project leads who need an exportable record of what was found and what the team decided about each finding.

1.3 AI and LLM integration

The system speaks the OpenAI /chat/completions protocol, so a single transport class covers four backends, selected by one line of configuration:

LLM_PROVIDER Endpoint Default model Cost
groq (default) https://api.groq.com/openai/v1 openai/gpt-oss-120b Free tier, no credit card
openrouter https://openrouter.ai/api/v1 google/gemma-4-31b-it:free Free tier
ollama http://localhost:11434/v1 llama3.1 Free, runs locally
openai https://api.openai.com/v1 gpt-4o-mini Paid

The model is reached through LLMClient, the single point of access, which wraps the transport in four decorators: retrying, caching, rate limiting and usage logging.

Where AI is actually used. Each call is labelled with a purpose, and the logging decorator accumulates tokens per purpose, so the system can report exactly what the model was used for: security-analysis, style-analysis, performance-analysis, maintainability-analysis, code-summary, test-generation, refactor-suggestion, chat-assistant, delta-summary, agent-planning, agent-decision and agent-synthesis.

1.4 Why this qualifies as meaningful agent behaviour

The Stage 2 instructions state that forwarding a prompt to an LLM API and displaying the response is insufficient. This implementation goes beyond that in six specific ways.

Required capability Where it is implemented What actually happens
Planning AgentPlanner.createPlan The goal plus the real repository inventory are turned into an ordered plan naming actual files. The plan is grounded: the planner is shown what exists so it cannot propose reading files that are not there.
Tool use ToolRegistry, five AgentTool implementations The agent selects a tool by name and passes it a string argument. It never executes model output as code. Tool descriptions are generated from the registry, so the catalogue and the prompt cannot drift apart.
Retrieval CodeRetriever A TF-IDF-weighted index over the repository. Questions and analyses are answered against the few regions that actually matter, which is what lets the assistant work on a codebase far larger than any context window.
Memory AgentMemory Short-term: the run’s observations, re-read before every decision. Long-term: the team’s accept/reject decisions, persisted to .agent-memory/memory.json and recalled by relevance into later prompts.
Decision making AgentPlanner.decideNextAction One action per turn, chosen from everything observed so far. A repeated action is blocked and the block is fed back as an observation the agent must react to. A tool error becomes an observation rather than terminating the run.
Multi-step execution AgentPlanner.run Plan → decide → act → observe → repeat → conclude, bounded by a configurable step budget so a run always terminates. Every step is published to both views as it happens.

A concrete example from a real run against samples/demo-project:

[step 1] PLAN         1. Call list_files to take an inventory of what the repository contains.
                      2. Call search_code to locate the code that handles credentials.
                      3. Call analyze_file with the security strategy on each file found.
[step 2] THOUGHT      Inventory the repository before choosing targets.
[step 2] ACTION       list_files
[step 2] OBSERVATION  Repository contains 3 source files ...
[step 3] THOUGHT      Locate the code most likely to handle credentials.
[step 3] ACTION       search_code: password authentication query
[step 3] OBSERVATION  Found 1 relevant region: LoginService.java (from line 26) ...
[step 5] ACTION       analyze_file: src/com/acme/shop/LoginService.java|security
[step 5] OBSERVATION  recorded 5 finding(s): [Critical] line 15: Credential hard-coded ...
[step 8] CONCLUSION   Audit complete

The agent is also adaptive. Rejecting a finding with a reason writes that decision to long-term memory; the next analysis of related code carries an instruction derived from it:

- The team REJECTED the finding "Division without a zero guard", saying: sessionCount is validated by the caller. Do not report this again unless the circumstances clearly differ.

1.5 Implementation status

Fully implemented and working: all thirteen features in section 2, both interfaces, ten design patterns, the LLM integration with four interchangeable backends, and the autonomous agent loop. All ten features proposed in Stage 1 are implemented; none were dropped.

Verification: 110 assertions pass in the dependency-free harness (./build.sh --check), plus a JUnit 5 suite (mvn test). Both the GUI and the CLI have been exercised end-to-end, and the real HTTP path has been verified against a mock OpenAI-compatible endpoint covering success, malformed output, a 401 and a retried 503.

Honest limitations

These are real and are not worked around:

  1. Output quality depends on the model. On a free-tier 70B model, findings are good on obvious defect classes (injection, hard-coded secrets, swallowed exceptions, missing guards) and weaker on subtle cross-file logic errors. The system constrains the model — a fixed JSON schema, a severity ceiling per strategy, line-number validation — but it cannot make a small model reason better.

  2. Offline mode is deliberately limited. With no API key the application still runs, using a built-in static analyser that derives findings from the code by regular expression. It is a fallback so the interface and the test suite work without a key; it does not reason, and both interfaces display an OFFLINE MODE banner whenever it is active. Every AI-based feature in the demonstration videos is shown running against a real model.

  3. Analysis is per-file. The retriever supplies related snippets as context, but a defect that only exists in the interaction between three classes may be missed.

  4. F08 compares snapshots, not arbitrary commits automatically. The user analyses one version, snapshots it, checks out the other, analyses it and snapshots that. Git provides the changed-file list; the tool does not check out commits on the user’s behalf, which is deliberate — silently changing a developer’s working tree would be unsafe.

  5. Refactorings are suggestions, never applied automatically. The tool shows a side-by-side comparison and offers to copy the result. It does not write to source files.

  6. No authentication or multi-user support. It is a single-user desktop tool.

3. Implemented design patterns

Ten distinct patterns are implemented. The Stage 2 requirement is five; the five from Stage 1 are all present, and five more were added where implementation revealed a real need.

3.1 Singleton — LLMClient

Design problem. Twelve different call sites need the language model. If each created its own client, the API credential would be duplicated across objects, there would be no single usage total to report, the response cache would be fragmented, and per-minute rate limiting would be impossible because no component would see the total outbound rate.

Participants and roles. llm/LLMClient.java is the Singleton. The nested private Holder class is the lazy initialisation holder.

Source files and methods. LLMClient.getInstance(), sendPrompt(...), sendConversation(...), getUsageStats(), reloadConfiguration().

How the implementation follows the pattern. The constructor is private; the only access is the static getInstance(). The instance is created by the initialisation-on-demand holder idiom: the JVM guarantees the nested class is loaded lazily and exactly once, which makes access thread-safe with no synchronisation on the common path. That matters because the Swing event thread and the agent’s background worker both call it.

Why the pattern is useful here. It is what makes usage able to report a single accurate token total for the session, and what lets RateLimitingProvider see every outbound call.

Match with Stage 1. The pattern is the same; its responsibilities are narrower. Stage 1 gave LLMClient the fields apiKey and instance and the jobs of credential storage, transport, rate limiting and prompt construction. In the implementation the credential lives in AppConfig and is never held in a field that could be serialised or printed; transport lives in OpenAiCompatibleProvider; rate limiting lives in a decorator. What remains is what Singleton is actually for: controlled single access. This is recorded as change C1 in section 4.

3.2 Strategy — the review strategies

Design problem. Issue detection, coding-standard checking, performance review and maintainability review share one shape — take code, produce findings — but differ in what they look for, how they are prompted, how severe their findings may be, and whether a deterministic pre-pass applies. Expressed as conditionals inside the agent, every future analysis type would concentrate in one growing method.

Participants and roles.

3.4 Observer — view updates

Design problem. Two independent views must reflect the same model, and the agent produces results incrementally from a background thread. Polling would waste cycles and lag; a direct reference from the model to a view would tie the model to Swing.

Participants and roles. observer/Subject.java (abstract subject), observer/Observer.java (observer interface), model/ReviewReport.java (concrete subject), ui/CodeReviewGUI.java and ui/CLIView.java (concrete observers).

Source files and methods. Subject.addObserver(...), notifyObservers(UpdateEvent, Object), Observer.updateUI(UpdateEvent, Object), ReviewReport.addItems(List), itemChanged(ReviewItem).

How the implementation follows the pattern. The subject holds observers in a CopyOnWriteArrayList — the agent notifies from a worker thread while the event thread may be registering views — and pushes typed events. One misbehaving view cannot stop the others: an exception thrown by an observer is caught and logged, which the test suite verifies.

Why it is useful here. It is what lets the agent’s reasoning stream live into the GUI trace panel and the CLI simultaneously, with no coupling between them.

Match with Stage 1. Two differences, both recorded as change C2: (a) Stage 1 declared updateUI() with no parameters, which would have forced every view to query the subject to discover what changed; the implemented signature passes the event and its payload so a view can repaint only the affected region. (b) Stage 1 named ReviewReport as the subject; that is still true, and Subject was extracted as an abstract base so the registry logic is written once.

3.5 Facade — ReviewAgent

Design problem. Behind the AI layer sit the Singleton client and its four decorators, the strategy registry and four strategies, the deterministic standards checker, the retrieval index, long-term memory, the tool registry and five tools, and the planner. A controller orchestrating those directly would need to know the order in which memory is recalled, context retrieved, rules loaded, prompts assembled and findings recorded — and both views would need to know it identically.

Participants and roles. agent/ReviewAgent.java is the Facade. Subsystems: LLMClient, StrategyRegistry, StandardsChecker, CodeRetriever, AgentMemory, ToolRegistry, AgentPlanner. app/AgentController.java is the client.

Source files and methods. analyzeFile(...), analyzeCode(...), summarise(...), generateTests(...), suggestRefactor(...), chat(...), runAudit(...), onRepositoryImported().

How the implementation follows the pattern. The controller calls one method and receives a result. Every facade method performs the same internal preparation — load conventions, recall decisions, retrieve related code, then call the model.

Why it is useful here. It is what keeps AgentController readable and what guarantees the GUI and CLI behave identically, since both go through the same six operations.

Match with Stage 1. The role matches. The interface is wider: Stage 1 declared analyzeCode() and generateTests(); the implementation exposes six operations because F02, F04, F08 and F10 each need a different prompt shape and return type. Forcing them through analyzeCode() would have meant callers inspecting the returned text to work out what they had been given. Recorded as change C4.

3.6 Composite — FileNode (added in Stage 2)

Design problem. RepoManager.loadFiles() was specified in Stage 1 to return a flat List. A flat list cannot express nesting, so the hierarchical file browser promised by F01 could not have been drawn from it, and statistics such as “how many files are under src/” would have required the caller to re-derive the structure from path strings.

Participants and roles. model/FileNode.java plays both Component and, depending on isDirectory, Leaf or Composite. Clients: the Swing JTree model, the CLI tree command, ListFilesTool, and the report header.

Source files and methods. getTotalFiles(), getTotalDirectories(), getTotalSizeBytes(), flatten(), find(String), render(int), add(FileNode).

How the implementation follows the pattern. Every operation is uniform: a leaf answers for itself, a directory recurses into its children and combines. Client code never asks whether a node is a file. add on a leaf is ignored rather than throwing, which keeps the uniform interface safe at the call site.

Why it is useful here. ListFilesTool, the GUI tree and the CLI renderer are each a few lines because the traversal lives in the model. Recorded as change C6.

3.7 Factory Method — provider and exporter creation (added in Stage 2)

Design problem. Two independent decisions are made at run time from configuration or user input: which LLM backend to talk to, and which format to export. Without a factory, LLMClient would contain a chain of conditionals naming four concrete transports plus the decorator assembly order, and both views would name four concrete exporter classes.

Participants and roles. llm/LLMProviderFactory.java and export/ExporterFactory.java are the creators; OpenAiCompatibleProvider and MockProvider, and the four exporters, are the products.

Source files and methods. LLMProviderFactory.create(UsageStats, Consumer), createTransport(), ExporterFactory.create(String), createForFileName(String).

How the implementation follows the pattern. Client code asks for “a provider” or “an exporter for pdf” and receives a fully configured object without naming a class. The provider factory also encapsulates the decorator assembly order and documents why that order is correct — logging outermost so cache hits count as served requests, caching above rate limiting so a cached answer is not delayed, retrying innermost so a retried call is counted once.

Why it is useful here. Adding a backend or a format is a change in one file. Recorded as change C7.

3.8 Template Method — analysis and export (added in Stage 2)

Design problem, two instances. (a) Every analysis performs the same seven steps in the same order, and only some of them vary; copied into each strategy, a fix to the JSON-repair logic would have to be made four times. (b) Every export produces the same document sections in the same order and only the markup differs.

Participants and roles.

Class Role
agent/strategy/AbstractReviewStrategy.java Abstract class defining the algorithm
SecurityStrategy, StyleStrategy, PerformanceStrategy, MaintainabilityStrategy Concrete classes supplying the varying steps
export/AbstractReportExporter.java Abstract class defining the document order
PdfExporter, MarkdownExporter, HtmlExporter, JsonExporter Concrete classes supplying markup

Source files and methods. AbstractReviewStrategy.executeStrategy(...) is final; abstract getRoleInstruction(), decoratePrompt(...), getPurpose(); hooks runDeterministicPass(...), getSeverityCeiling(), postProcess(...); shared parseFindings(...), validate(...). AbstractReportExporter.export(...) is final; abstract writeHeader/Summary/Findings/DecisionRecord/Footer; hooks writeExtraSections, writeToDisk.

How the implementation follows the pattern. The template methods are final, so a subclass can customise the steps but never their order. The hooks have useful defaults: only StyleStrategy overrides the deterministic pass, and only PdfExporter overrides writeToDisk.

Why it is useful here. PdfExporter is the clearest payoff: a format whose output is not text at all still reuses the document order, the grouping, the sorting and the error handling, by overriding one hook. Recorded as change C8.

Relationship to Strategy. They sit on the same class hierarchy but answer different questions. Strategy decides which analysis runs; Template Method decides how every analysis runs. They are counted separately because they address separate design problems.

3.9 Decorator — the provider chain (added in Stage 2)

Design problem. Retrying, caching, rate limiting and usage accounting are four independent concerns that apply to every model call. Inside OpenAiCompatibleProvider they would produce one class with four reasons to change, and all four would have to be duplicated in the offline provider.

Participants and roles.

Class Role
llm/LLMProvider.java Component interface
llm/OpenAiCompatibleProvider.java, llm/MockProvider.java Concrete components
llm/decorator/LLMProviderDecorator.java Abstract decorator
RetryingProvider Retries retryable failures with exponential backoff
CachingProvider LRU cache of identical requests
RateLimitingProvider Enforces a minimum gap between calls
LoggingProvider Accumulates tokens and latency into UsageStats

Source files and methods. LLMProvider.complete(LLMRequest) implemented by every layer; LLMProviderDecorator.inner; LLMProviderFactory.create(...) composes the chain.

How the implementation follows the pattern. Each decorator both implements and wraps the component interface, so a decorated provider is indistinguishable from a bare one at every call site, and layers can be stacked in any order. The chain’s name reports itself: Groq(openai/gpt-oss-120b)+retry(3)+ratelimit+cache+logging.

Why it is useful here. RetryingProvider is the implementation of the alternative flow in sequence diagram SD01 and use case UC02: a timeout is retried automatically before the user sees anything. LoggingProvider is what makes section 5 of this report quote measured token counts rather than estimates. Recorded as change C9.

3.10 Memento — undo state (added in Stage 2)

Design problem. Undo must restore a finding’s exact prior triage state. Having each command store the fields it changed would spread knowledge of ReviewItem’s internals across four command classes, and adding a mutable field later would silently break undo for all of them.

Participants and roles. model/ReviewItem is the Originator; its nested ReviewItem.Memento is the Memento; the command classes are Caretakers.

Source files and methods. ReviewItem.createMemento(), ReviewItem.restore(Memento); previousState in each command.

How the implementation follows the pattern. The memento’s fields are private to the nested class, so a command can hold it and hand it back but cannot read or alter the captured values. The originator decides what state is worth capturing; adding a new mutable field means changing ReviewItem only.

Why it is useful here. The test undoRestoresThePreviousCommandsStateNotTheDefault verifies the property that matters: after accepting with a note and then rejecting, undo restores the accepted state with its original note, not a blank default. Recorded as change C10.

3.11 Builder — PromptBuilder (supporting)

A prompt is assembled from up to eight independent parts, most call sites need only some, and order matters. A constructor taking eight nullable strings would be unreadable. llm/PromptBuilder.java lets each strategy name only the parts it needs, keeps the assembly order in one place, and enforces the context-window guard rail in build().

    2. The system takes an inventory of the repository and asks the model for a plan grounded in the files that exist.

  • Alternative flows: Nothing matches, and the user is told so and offered the file list.

4. Changes and rationale

Consolidated record in the form Original design → Implemented change → Reason → Impact.

4.1 Feature changes

C-F1 — F08 comparison scope narrowed

  • Original design (F08). “User selects two commits in the repository browser to compare”; the system fetches diffs and compares historical data.
  • Implemented change. The user analyses a version, saves a labelled snapshot, switches version themselves, analyses and snapshots again, then compares the two snapshots. Git supplies the changed-file list and the commit list.
  • Reason. Checking out a commit silently rewrites the developer’s working tree, which can destroy uncommitted work. The tool does not take that liberty. The comparison logic — the valuable part — is unchanged and fully implemented.
  • How it addresses the original need. The user still gets exactly the delta report F08 specified: resolved, newly introduced and still-present findings, with an AI verdict on the direction of travel.
  • Affected artefacts. UC04; ReviewSnapshot, DeltaReport, RepoManager.getDiff, AgentController.compareSnapshots; no pattern change.

C-F2 — F06 split made explicit

  • Original design (F06). “Hybrid (deterministic parsing + AI interpretation of vague rules)”.
  • Implemented change. The split is enforced structurally: StandardsChecker decides every mechanical rule, and the model’s prompt carries the active rules plus an instruction not to report them.
  • Reason. Without the exclusion both halves report the same violation, producing duplicate findings that each need triaging separately. This was observed during testing and fixed.
  • Impact. StyleStrategy overrides the Template Method’s deterministic hook; verified by the tests conforming code produces no findings and a rule turned off in .rules does not fire.

C-F3 — F09 extended to four formats

  • Original design (F09). Export to PDF or Markdown.
  • Implemented change. PDF, Markdown, HTML and JSON.
  • Reason. HTML is the format a report is actually shared in; JSON makes the tool usable from a CI pipeline and lets a session be reloaded. Both were nearly free once the Template Method base existed.
  • Impact. Four exporters behind ExporterFactory; adds Factory Method and the second Template Method instance.

C-F4 — F11 added: Autonomous Multi-Step Repository Audit

  • Original design. No equivalent. Stage 1 described the agent’s capabilities but every feature was a single request-response call.
  • Implemented change. A full plan → decide → act → observe → conclude loop with five tools, short- and long-term memory, loop protection and a step budget.
  • Reason. The Stage 2 instructions require reasoning, planning, tool use, retrieval, memory, decision making or multi-step execution, and state that forwarding a prompt is insufficient. Reviewing the Stage 1 design against that requirement showed that none of the ten features individually satisfied it. F11 is the feature that makes the system an agent.
  • Scope impact. This is the largest addition. It introduced agent/AgentPlanner, AgentStep, AgentMemory and the whole agent/tools package.
  • Affected artefacts. New UC06; new SD04; AgentPlanner, AgentMemory, ToolRegistry, five tools, AnalysisService; uses Facade, Singleton and Strategy.

C-F5 — F12 added: Undo, Redo and Action History

  • Original design. Stage 1’s ReviewCommand declared only execute(), and listed “undo operations” as a motivation for the Command pattern without a feature to deliver it.
  • Implemented change. undo() and getDescription() added to the interface; CommandHistory with undo and redo stacks plus an append-only log; BulkTriageCommand so a batch undoes as one step.
  • Reason. Rejecting a finding writes a permanent decision into agent memory. Without undo, a misclick teaches the agent something wrong with no way to correct it. The pattern was already in place; the feature was two methods away.
  • Impact. Adds Memento; extends UC04 and SD02.

C-F6 — F13 added: Codebase Search and Retrieval

  • Original design. F10 described sending “chat text + code context” to the model, with no mechanism for choosing that context.
  • Implemented change. CodeRetriever, a TF-IDF index over the repository, exposed as a user-facing search, as the agent’s search_code tool, and as the context source for F10 and for every analysis.
  • Reason. A codebase does not fit in a context window. Without retrieval, F10 could only answer about the file currently open, which is not what “ask about the codebase” means.
  • Impact. New UC07; CodeRetriever, SearchCodeTool; makes F10 substantially better.

C-F7 — Four analysis strategies instead of two

  • Original design. SecurityStrategy and StyleStrategy.
  • Implemented change. Added PerformanceStrategy and MaintainabilityStrategy, plus a “Full review” action that runs all four.
  • Reason. Security and style covered correctness and formatting but left algorithmic cost and structural design unexamined — and F04 and F05 produce noticeably better output when a maintainability pass has run first.
  • Impact. Two new classes, two registry lines, no change to ReviewAgent.

C-F8 — No feature was removed

All ten Stage 1 features are implemented. Nothing was silently dropped.
